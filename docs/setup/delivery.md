## Local and CI checks

`npm run check` runs formatting, Oxlint, TypeScript, operational-script tests and a build with real connection/auth/storage variables cleared. That build artifact must never be deployed. `npm run verify` adds the mobile and desktop browser suite. `npm run test:services` separately checks real isolated Neon/Postgres and private storage using an external deterministic Auth fixture. `npm run test:live` requires a real Google session and tests the deployed application.

`.github/workflows/ci.yml` runs `quality` and `end-to-end` for PRs and main pushes. Node.js follows `.node-version`; installs use `npm ci`. Official Actions are pinned to verified complete commit SHAs. PR jobs have read access and no environment credentials. Failure reports are retained for seven days. Playwright rejects `.only` in CI, retries once, and closes its test servers gracefully. Forks and Dependabot never run deployment jobs with environment secrets.

Dependabot groups Next/React, Neon and AWS SDK updates and checks Actions monthly. The PR template records verification, migrations and absence of private data. `SECURITY.md` directs vulnerabilities to private reporting.

## Database provisioning and migration

The existing deployed test app uses `bottom_shelf_app_runtime`, a SQL-created login with no Neon admin membership, no RLS bypass, and no role/database creation rights. The temporary API-created role was removed after it was found to have elevated Neon privileges.

`DATABASE_URL` is the runtime connection. `DATABASE_MIGRATION_URL` is a separate direct owner connection, never transferred to Vercel. For a fresh isolated test environment, configure the direct owner URL and `APP_ENV=test`, then run `npm run db:provision`. It saves credentials first in a private, ignored `.env.local.runtime-pending` file, then commits the role and atomically replaces `.env.local`. The pending file is preserved on failure, including an unknown COMMIT outcome. Rerunning verifies a committed login or recreates a rolled-back role with the same saved password before recovering the configuration. Do not delete or publish a pending file. Existing role passwords are not reset. Do not create runtime roles through Neon Console/API: they inherit elevated privileges.

`npm run db:migrate` validates that applied migrations are an unchanged prefix of the local files. Removed, reordered or edited applied files fail. New SQL and migration records run in one transaction under a transaction-scoped advisory lock with a ten-second lock timeout. Migration 002 grants only SELECT/INSERT/DELETE on the temporary probe table. Future tables need explicit reviewed grants. `npm run db:check` verifies the role and its restricted permissions.

## Staged deployment

`npm run deploy:test` follows: Vercel builds source without moving the domain → migration → runtime-role check → landing-page and anonymous-access smoke test → promotion. It validates the dedicated test project and, in CI, requires main. CLI version 63.1.2 is pinned. The protected staged host is tested using `vercel curl` platform authorization; no application session is passed. The app's private route must still return 401 with no-store.

Captured CLI failures report the exit status and bounded provider diagnostics after masking known secret environment values and credential patterns. Do not enable unrestricted debug logs to investigate a deployment failure.

The first CI failure was reproduced with Node.js 24.21.0 and CLI 63.1.2 in a clean Linux container. `--scope visegue` triggers a user-profile lookup, which returns 404 for the CI token even though that token can access the project. The local CLI's cached team mapping hid this problem. Deploy and smoke commands now use `VERCEL_ORG_ID`/`VERCEL_PROJECT_ID` in CI, or the verified local project link, without `--scope`. The unused scope variable is no longer required by CI. Removing that flag allowed the real Linux staged deployment and smoke checks to pass.

The CLI's promotion command also requires a user profile independently of `--scope`. With `VERCEL_TOKEN` present, promotion therefore uses the same project-scoped REST endpoint as the CLI: first verify the deployment's project, team, READY state and production target; then request promotion; then verify the project's production deployment ID, allowing up to 60 seconds for confirmation. API errors expose only HTTP status. Local use without an explicit token retains CLI authentication. The project-scoped API returned 201 with the supplied CI token and the production target was independently verified. The GitHub deployment job passed after the correction reached `main` in PR #25 on 2026-10-18.

Final local verification on 2026-10-15 passed formatting, lint, typecheck, 16 script tests and the build check. Both review axes reported zero findings. The actual corrected smoke and promotion modules then passed in Linux with the supplied CI token; Vercel's production target was confirmed as `dpl_EqgY6hTZFb8qC4XMdMrqyqKHmDzY` (`https://bottom-shelf-2ii2xtv4b-visegue.vercel.app`). This deployment contains the already published app code. The user explicitly authorized a PR for the follow-up CI correction on 2026-10-15; no successful GitHub deployment run is claimed.

Vercel's automatic Git deployments are disabled in `vercel.json` so a future Git integration cannot skip the gates. Deployment checks do not substitute for a real Google session or the deployed owner-scoped database/storage probe.

A failed stage leaves the previous deployment on the domain. Database migrations may already be applied; they are not automatically rolled back. Keep migrations compatible with the prior app version and use separate expand/contract releases for destructive changes. Diagnose the first failed step, never edit applied migration history to make CI pass. This pipeline does not create release tags or GitHub Releases.
